Interactive
How a query travels
This is how one search request moves through the product I run for a Noida software company: a multi-tenant AI product-search platform. Click each step to see what happens and how fast it is.

      

        

        
Step 1 of 5
A shopper types or speaks
A query arrives in plain language, like “gift for someone who cooks”. It comes typed or spoken from the storefront widget or either of the two React dashboards, since I put a Web Speech API microphone in all three. The shopper does not need to know the right keywords.
 3 entry points · text or voice
Step 2 of 5
Long queries get an LLM step
I send queries of six or more words through an LLM intent step. It pulls out the core product, price limits and attributes, so a stated price or stock limit survives every fallback. The result is cached for 24 hours and the step fails open: if the LLM does not answer, search still runs.
 cached 24 h · fail-open
Step 3 of 5
The words become 3,072 numbers
The query becomes a vector with OpenAI text-embedding-3-large: a list of 3,072 numbers that stands for its meaning. I embed every product the same way, so the search compares meaning, not spelling. A two-tier embedding cache remembers past queries, so a repeat query comes back in about 0 ms.
 3,072 dimensions · repeats ~0 ms
Step 4 of 5
OpenSearch finds the nearest products
OpenSearch runs a k-NN vector search to find the products whose vectors sit closest to the query. I made this stage one pass instead of several and moved the search calls off the event loop, so they never block the API. With the cache, search latency fell from about 500 ms to 150-250 ms.
 ~500 ms → ~150-250 ms
Step 5 of 5
Results go back, small and scoped
I compress the results with gzip, which cut responses from 83 KB to 19 KB. For a voice query, an LLM writes a short spoken summary and text-to-speech reads it back. Every call in this chain is scoped by client_id behind per-tenant isolation guards, proven by a 31-test tenant-isolation suite I wrote.
 83 KB → 19 KB · 31 tests
Query in→Intent→Embedding→Search→Response

CASE 01
Product Search That Understands Meaning
Search latency cut from ~500 ms to ~150-250 ms, repeat queries ~0 ms.
Problem
I am the technical owner of bCloud AI Search, a multi-tenant AI product-search SaaS with 70+ FastAPI endpoints. Its search matched keywords only, so a shopper typing "gift for someone who cooks" got nothing useful.
What I did
I built the semantic core: OpenAI text-embedding-3-large, 3072-dimension vectors, indexed into OpenSearch, so plain-language queries return relevant products. I made it fast with a two-tier embedding cache, single-pass query execution and off-event-loop search calls, and made it small with gzip. Longer questions go through an LLM intent step that pulls out the core product, price limits and attributes, so stated price and stock limits survive every search fallback.
Result
Search latency went from ~500 ms to ~150-250 ms, and repeat queries return in ~0 ms. Responses shrank from 83 KB to 19 KB with gzip.

CASE 02
Dead Search Platform Brought Back
255,350 products re-indexed with zero errors in 1 hour 52 minutes, backend untouched.
Problem
A large e-commerce marketplace had a dead AWS-based search platform. The client froze the backend code: no changes allowed, not one line.
What I did
I wrote a local TLS/SigV4 compatibility shim that copies AWS's own TLS handshake and request signing, so backend code written for AWS OpenSearch Serverless ran unmodified against self-hosted OpenSearch on Azure. Around it I built a FastAPI service powering two new React dashboards behind nginx, plus idempotent bash installers that redeploy the whole stack with one command. I also fixed a silent analytics event-loss bug with a schema repair script.
Result
I re-indexed 255,350 products with zero indexing errors in 1 hour 52 minutes. The client's backend ran unmodified, so the zero-code-change constraint held.
OpenSearchFastAPIReactnginxBashAzure

The product needed voice search: let a shopper talk instead of type, in the storefront widget and both dashboards. Every voice query also had to show up in billing and analytics.

I shipped voice search end to end. A Web Speech API microphone sits in the storefront widget and both dashboards, and the API returns results plus an LLM spoken summary that text-to-speech reads back. I folded the voice AI cost into per-request billing and added a by-source analytics tab.
Result
Voice search is live in the storefront widget and both dashboards, with its AI cost billed per request. On the same platform I ship an LLM helpdesk agent with three production tools, and a 31-test tenant-isolation suite proves no tenant can reach another tenant's data.

CASE 05
Taking Over a Live FinTech Platform
Inherited a live payments platform: four critical security findings and one silent revenue leak.
Problem
A FinTech platform (SplitIT) lost its original developer mid-project. It was live and handling real money through Stripe Connect, Stripe Financial Connections, ACH debits, automated payouts and PayPal Billing.
What I did
I took over as sole developer and now own the codebase (React, TypeScript, Express, PostgreSQL), the AWS infrastructure (RDS, ECS Fargate, CloudFront), backups, releases and client-facing technical responses. I ran a security audit, wrote the plan to fix the findings, and took full production backups before a controlled infrastructure pause. Reading the payment code, I found that no PayPal webhook was registered.
Result
The audit documented four critical findings: an unauthenticated payment endpoint, an IDOR, sensitive data in logs and secrets committed to environment files. The missing webhook was a revenue-affecting gap: subscriptions expired silently while customers kept being billed.
